维护责任角色为网站技术/内容维护负责人，发布仍由父级审查决定。触发是官方改订/勘误/法令公布及生效日前核对；日历每年2月官方公布次年表时核对春秋分，社保3–4月、给付8月、最低工资地方生效日前、税制按官方所得年/课税年度核对。触发不等于核验完成，未来未公布字段保持 unknown，不能只改页面年份或 reviewed 日期。

现有机制已足够，无需新增云端cron：

1. 依据官方材料更新数据/页面和独立样例，确认每项适用范围；动态JST输入已有运行时处理，不能依赖云端重建修复输入跨年。
2. 静态年度表/下载明确固定版本。营业日只支持2026/2027；日出城市表的基准年/基准日由构建时确定，跨年需要维护负责人确认后重建，动态指定日期仍按输入计算。
3. 有日历数据变更时，Node22运行 `node scripts/generate-work-calendar.mjs`（npm prebuild也执行）生成固定2026/2027 CSV/JSON/ICS，脚本先与已核官方日期fixture比较。不自动加入2028。
4. 若实际影响PDF，才运行 `scripts/generate-business-pdfs.mjs` / `scripts/generate-age-pdfs.mjs`，使用已有Playwright/Chromium和日文字体环境，检查受影响文件。Excel复用现有手工/专用流程，未知复现能力先标阻塞，不以文件存在冒充兼容性通过。本轮给付修复没有关联下载，不重新生成或认证所有PDF/Excel。
5. 网站内容提交后 `node scripts/update-lastmod.mjs`，manifest-only独立提交，再相关测试及一次 `npm run build`；审核候选diff和受影响产物，获得部署授权后才发布。
